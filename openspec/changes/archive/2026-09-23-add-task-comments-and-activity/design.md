# Design

## Context

See proposal.md for why. The parts of the current code that shape the approach:

- `src/lib/tasks.ts` is the only module that touches the database. `createTask`, `updateTask` and `moveTask` already run inside `db.transaction(...)`, and helpers take a `Conn` (the db or an open transaction).
- Task changes come from three places: the create dialog (`createTaskAction`), the detail page, which saves one field at a time through `updateTaskAction`, and the board, which calls `moveTaskAction` on drop. `moveTask` renumbers every card in the target column, so it writes many rows even when only one task changed status.
- `updateTask` receives partial input. Labels come in as a full list of ids (`labelIds`), not as add/remove operations.
- `src/lib/db/index.ts` runs `PRAGMA foreign_keys = ON` and applies drizzle migrations on open, so `ON DELETE CASCADE` works and a new migration is picked up by the app, the tests (`:memory:`) and `npm run db:migrate`.
- Client Components may only `import type` from the data layer. Pages are Server Components and do the formatting of dates today (`formatDateTime` is called in `tasks/[id]/page.tsx`).
- `openspec/specs/` is empty, so all three capabilities are new (see specs/).

## Goals / Non-Goals

**Goals:**
- Record activity in the data layer, in the same transaction as the change, so no caller can forget it and a failed update leaves no half-written history.
- Keep the migration purely additive (two new tables), generated by drizzle-kit.
- Keep the timeline readable over time even if labels are renamed or deleted.

**Non-Goals:**
- Recording who made a change (single user, no author field).
- Activity for comments, or for changes to labels themselves (rename, delete).
- Backfilling history for tasks that exist before the migration.
- Pagination of the timeline, real-time updates, or undo.

## Decisions

### D1. Two tables, not one polymorphic "timeline" table
`comments(id, task_id, body, created_at, edited_at)` and `task_activity(id, task_id, field, from_value, to_value, created_at)`, both with `task_id REFERENCES tasks(id) ON DELETE CASCADE` and an index on `(task_id, created_at)`. Comments are editable and deletable; activity is append-only. Keeping them apart keeps each table's rules simple (for example `body NOT NULL` only applies to comments). The timeline is merged in the data layer.
- Alternative: one `timeline_entries` table with a `kind` column. Rejected: nullable columns for one kind or the other, and editing rules that apply to half the rows.

### D2. `edited_at` nullable column, not `updated_at`
A comment is "edited" when `edited_at IS NOT NULL`. It is set only when an update changes the body.
- Alternative: compare `updated_at > created_at`. Rejected: a no-op save would still mark it edited, and millisecond timestamps make the comparison fragile in tests.

### D3. Activity stores the raw stored values as text
`field` is one of `created | title | description | status | priority | labels | due_date`. `from_value` / `to_value` are text and nullable: status and priority store their codes (`in_progress`, `urgent`), due date stores `YYYY-MM-DD`, title and description store the text, and `created` stores nothing. Turning codes into display names ("In Progress", "Urgent") happens at render time with the existing `STATUS_LABELS` / `PRIORITY_LABELS`, so the display can change without a data migration.
- Alternative: store the finished sentence. Rejected: it freezes wording and cannot be tested per field.

### D4. Labels stored as a name snapshot
For `labels`, `from_value` / `to_value` hold the sorted label names joined with ", " (empty list = null). This is what the spec requires ("still reads correctly if a label is renamed or deleted"). Label ids would break when a label is deleted.
- Alternative: one entry per added / removed label. Rejected: `updateTask` receives a full list, and the request asks for "from what to what", which a before/after list gives directly.

### D5. Diff inside `updateTask` and `moveTask`
`updateTask` already loads the current row; it will also load the current label names, compare each field in the parsed input with the current value, and insert one activity row per real change before returning. `moveTask` records a `status` entry only for the moved task and only when its status actually changes; the renumbering of the other cards is not recorded. `createTask` inserts one `created` row. All inserts use the transaction handle.
- Alternative: SQLite triggers. Rejected: label names live in another table, triggers are hard to see and test from TypeScript, and the project keeps all logic in `src/lib/tasks.ts`.

### D6. Timeline merged in the data layer
A new `getTimeline(taskId)` returns a single array of `{ kind: "comment" | "activity", ... }` entries sorted by `created_at`, with a stable tie-break (activity before comments at the same millisecond, then id). The page passes it to a Client Component. Dates are formatted on the server (same as today's "Created"/"Updated") so server and browser agree.

### D7. Comment count through a grouped subquery
`listTasks` and `getTask` add `commentCount` to each task by running one `SELECT task_id, count(*) ... GROUP BY task_id` for the loaded ids, like `withLabels` does for labels. This keeps one extra query per list, not one per task.
- Alternative: a stored counter column on `tasks`. Rejected: it changes the existing table and can drift.

### D8. Code stays in the existing files
Comment and activity functions go into `src/lib/tasks.ts`, because CLAUDE.md says it is the only place that reads or writes the database. The comment zod schema goes into `src/lib/validation.ts`, the actions into `src/app/actions.ts` (returning the existing `ActionResult`), and the sentence builder into `src/lib/format.ts` so it can be unit tested without a DB. New UI lives in `src/components/Timeline.tsx`.

### D9. Delete confirmation
Deleting a comment asks for confirmation with `confirm()`, the same way deleting a task does today.

## Risks / Trade-offs

- [Activity rows grow without limit, one per field change] → Rows are tiny and the app is single-user; an index on `(task_id, created_at)` keeps the timeline query fast.
- [Description changes store the full old and new text] → Up to 2 × 20,000 characters per edit. Acceptable for a local single-user app, and it keeps the option to show a diff later.
- [A future code path could write to `tasks` without going through `updateTask`/`moveTask`] → The data layer is the only writer by convention, and unit tests cover every tracked field.
- [Tasks created before the migration have no "created" entry] → Accepted and stated in the spec. Backfilling would add a data step to a schema migration for little value.
- [Same-millisecond ordering] → Stable tie-break by kind and id (D6).

## Migration Plan

1. Add both tables to `src/lib/db/schema.ts` and run `npm run db:generate -- --name comments_and_activity`. Commit the generated SQL and snapshot; do not edit `0000_init.sql`.
2. The migration only runs `CREATE TABLE` and `CREATE INDEX`, so existing rows in `tasks`, `labels` and `task_labels` are not touched. Verify by migrating a database seeded on master and comparing the rows before and after.
3. The app applies the migration on first open. Rollback: check out master and restore the database file from a copy, or drop the two new tables; nothing else depends on them.
4. `seed()` keeps working because deleting tasks cascades to the new tables.
